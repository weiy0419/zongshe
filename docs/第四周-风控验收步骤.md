## 2. 完整调用链

```text
POST /api/risk/assess
  → RiskController.assess
  → RiskService.assess / RiskServiceImpl.assess
  → 校验策略，读取已提交申请和关联用户，核对请求输入
  ├─ 未提供 productId：明确 MISSING_PRODUCT_ID，跳过去重
  └─ 提供 productId：校验产品存在 → RiskAssessmentDedupService.assess
       ├─ 命中缓存：读取已计算 Result，不调用计算回调
       └─ 未命中：SET NX 锁 → 二次读缓存 → 调用计算回调
  → TwoStageRiskOrchestrator.assess（仅未命中/跳过去重/用户输入变化时）
       → FeatureContextService.build
       → 硬规则准入
       → 准入通过且 WOE 启用：ScoringCardRiskEvaluator
           → WoeScoringCardEngine.evaluate
       → Result
  → 去重服务对非 MANUAL_REVIEW 结果执行 Lua 发布，TTL 120 秒
  → RiskReportAssembler.assemble，绑定当前 applicationId、userId
  → RiskReportDTO，breakdown.dedup 标明是否复用
```

实际生产特征与仓库读取在本次组件测试中使用固定输入/模拟仓库；MockMvc 没有经过 JWT 过滤器和网关。

新 assess 接口只读数据库，`reportId=null`。旧 `/applications/{id}/assessment`、`/report` 仍走旧查询或评估入口，不应当作本次新报告的查询或历史回放接口。

## 4. 真实环境验收前提

1. 使用已启动的测试 MySQL、Redis、backend 和 gateway，确认网关 8088 可访问后端。
2. 在风控配置中确认 `risk.scoring-card.engine=woe`、`risk.scoring-card.enabled=true`、`risk.scoring-card.pass-min-points=40`。本轮不修改表结构或自动造数。
3. 准备已经提交并完成事务提交的测试申请 ID，以及调用方确认对应的真实产品 ID。当前申请实体没有产品关联字段，服务只能核验产品存在，不能替调用方证明产品归属。
4. 选取能返回 APPROVED 或明确 REJECTED 的稳定样本。MANUAL_REVIEW 当前不缓存，不适合演示缓存命中。
5. 获取有效 JWT；把 token 设置在当前 PowerShell 的 `WEEK4_TOKEN` 环境变量中，不写入文档或提交到 Git。
6. 确保目标键已自然过期或使用未评估过的测试样本。不执行 FLUSHDB/FLUSHALL，不清空共享 Redis。

## 5. 第一次/第二次 HTTP 请求

在 PowerShell 中执行，ID 输入真实测试数据：

```powershell
$week4BaseUrl = 'http://localhost:8088'
$week4ApplicationId = [long](Read-Host '已提交的申请 ID')
$week4ProductId = [long](Read-Host '对应的真实产品 ID')
if (-not $env:WEEK4_TOKEN) { throw '请先在本地环境变量 WEEK4_TOKEN 中配置 JWT' }
$week4Headers = @{ Authorization = "Bearer $env:WEEK4_TOKEN" }
$week4Body = @{
    applicationId = $week4ApplicationId
    productId = $week4ProductId
    enabledModels = @('WOE')
} | ConvertTo-Json -Compress

$week4First = Invoke-RestMethod -Method Post -Uri "$week4BaseUrl/api/risk/assess" `
    -Headers $week4Headers -ContentType 'application/json' -Body $week4Body
$week4Second = Invoke-RestMethod -Method Post -Uri "$week4BaseUrl/api/risk/assess" `
    -Headers $week4Headers -ContentType 'application/json' -Body $week4Body

if ($week4First.decision -eq 'MANUAL_REVIEW') { throw '本样本转人工且不缓存，请检查原因或换稳定样本' }
if ($week4First.breakdown.dedup.reused -ne $false) { throw '首次已命中旧缓存，请等目标键过期后重试' }
if ($week4Second.breakdown.dedup.reused -ne $true) { throw '第二次未命中，请检查产品 ID、TTL、Redis 和用户输入是否变化' }
if ($week4First.totalScore -ne $week4Second.totalScore) { throw '两次分数不一致' }
if ($week4First.decision -ne $week4Second.decision) { throw '两次决策不一致' }
if ($week4First.assessedAt -ne $week4Second.assessedAt) { throw '第二次没有保留首次评估时间' }

$week4First | ConvertTo-Json -Depth 20
$week4Second | ConvertTo-Json -Depth 20
```

通过样本还应确认 `cardVersion=woe-card-v1`，`scorecardDetails.breakdown` 内有 `woe`、`factor`、`parameterSource=EXPERT_DEMO`。准入直接拒绝的样本应有原因码、`stage=ADMISSION`，申请卡 skipped，不要求有申请卡分数。

## 6. Redis 与日志证据

在 Redis 所在测试环境，用已有连接方式查询本次日志给出的**完整 key**：

```text
TTL risk:assessment:w4-v2:{用户主键:产品ID:金额桶:金额评分区间:WOE}
GET risk:assessment:w4-v2:{用户主键:产品ID:金额桶:金额评分区间:WOE}
```

花括号是 key 的实际组成部分，需保留；版本以运行配置为准。例如固定组件测试使用 `risk:assessment:w4-v2:{2:7:10:LE_50000:WOE}`，不要把这些示例 ID 当作真实数据。

验收证据：

- 第一次结束后结果键 TTL 接近 120 且持续下降；第二次命中不把 TTL 重置为 120。
- 首次日志出现“开始计算，reused=false”及评分卡计算日志。
- 第二次出现“缓存命中，未重算，reused=true”，同一请求过程不新增评分卡计算日志。
- 等待该结果键实际过期，再请求，应 `reused=false` 并重新执行 WOE。无须删除任何键。
- Lua 原子性、锁持有者校验与并发冲突需要真实 Redis 专项验证；内存替身测试不能替代这些结果。

## 7. 其他必验用例

| 用例 | 操作 | 预期 |
|---|---|---|
| 相近申请 | 同用户、同产品，已提交申请金额分别 10000 和 10001，连续评估 | 第二笔 reused=true，但 applicationId 为第二笔；计算快照仍保留首次输入 |
| 关闭 WOE | 先缓存 WOE 通过结果，再传 `enabledModels=[]` | 准入照常，MANUAL_REVIEW，申请卡 DISABLED、分数 null，不能复用旧通过结果 |
| 缺少产品 | 去掉 productId 连续请求两次 | 两次 reused=false，skipped=MISSING_PRODUCT_ID；不能把此路径当作去重验收 |
| 金额边界 | 准备已提交的 50000/50001、200000/200001 申请 | 各边界两侧使用不同 key，不能跨评分区间复用 |
| 准入拒绝 | 使用已有信用不足或其他硬规则拒绝样本 | REJECTED，准入原因码非空，申请卡 ADMISSION_NOT_PASSED |
| 身份/输入不一致 | 请求 userId 或 loanAmount 与申请不一致 | HTTP 400，不覆盖数据库输入，不生成伪评估 |
| 用户输入变化 | 使用测试环境既有变更场景，使信用分/状态与缓存不同 | reused=false，USER_INPUT_CHANGED，重新计算；不要临时修改真实用户数据 |

金额边界测试要使用不同的已保存申请；不能只改请求中的 loanAmount，否则会被一致性校验拒绝。

## 8. 第四周整体验收尚存阻塞

1. 信贷 `submitApplication` 在事务提交前同步 HTTP 调用风控；新接口读取数据库，可能查不到该申请。应由信贷负责人调整调用时机。
2. 该调用只发送 applicationId/enabledModels，不发送 productId，因此当前申贷路径会明确跳过去重。
3. 信贷 HTTP 调用未显式携带 JWT，而 `/api/**` 要求认证；需检查 RestTemplate 是否另有统一鉴权设置，联调时确认实际认证。
4. 策略 GET 与 assess 在同一个 try 中，策略获取失败会直接进入 RISK_PENDING，没有落实第四周允许的默认 WOE 后继续评估。
5. 信贷成功分支未把 decision/reasonSummary 写回申请，并读取 DTO 中不存在的 passed 字段；页面闭环还未完成。
6. 新 assess 报告未落库，reportId=null；旧查询入口不是新两阶段报告的查询入口。

以上是验收发现，不在本轮修改。第五周公示独立模型、AHP、历史回放不属于本次验收实现范围。
